Driving Blender with MCP, into Unity, Godot or Unreal

Two diagrams, pros and cons for each engine, and a fourth option of my own. It's written for a solo developer with 4 weeks, a prototype that puts atmosphere first, heavy reliance on AI-generated procedural content, and a monthly token budget.

Solo dev4 weeksPrototype only (≈10 min) Atmosphere firstContinues after week 4$20–40 / month token budget
Short version
  • All three engines work with a Blender MCP. The real differences are how well the engine side can be driven by text and how fast the edit loop is.
  • My proposal: a script-first, manifest-driven pipeline. Claude writes bpy scripts that live in your repo and run headless. Blender exports .glb plus a manifest.json, and one small importer script in the engine places everything. MCP is for look-dev only, not bulk work.
  • Engine pick for this prototype: Godot 4 as the default, because its text-based scenes and GDScript suit AI editing and token economy. Choose Unity URP/HDRP if you already know it. Choose Unreal only if you want Lumen's look and accept the iteration cost.

Diagram 1 · Architecture: who talks to what

One AI client drives two MCP servers: one for Blender, one for the engine. Assets cross between them as files on disk. The MCP servers never carry mesh data, which keeps tokens down and the pipeline engine-agnostic.

Diagram 2 · Sequence: one lighthouse asset, end to end

The same loop applies to every engine. Build in Blender, look at it (screenshot), fix, export, import, look again. Only the engine-side import step differs.

Pros and cons per interaction

Ratings are judged against your constraints: solo, 4 weeks, atmosphere first, AI-heavy, token-limited, and a project that carries on past the prototype.

Blender → Unity Blender MCP + Unity MCP · C#

Pros

  • C# is strongly represented in AI training data, so generated gameplay code is generally reliable.
  • Asset Store covers the gaps: water, weather, fog, stylised ocean shaders.
  • HDRP gives volumetric fog, a water system and strong lighting for storm mood.
  • Mature Steam pipeline and controller support (Input System).
  • Boat physics via Rigidbody and buoyancy assets are well documented.

Cons

  • Scenes, prefabs and materials are YAML with GUIDs. AI edits to them are fragile, so you depend on the MCP bridge or editor scripts.
  • Domain reload after each script change makes the loop slow, and slow loops burn tokens.
  • URP vs HDRP is a one-way door. HDRP looks best but is heavier, and you pay for it in setup.
  • glTF needs a package. FBX loses custom properties unless you plan for it.
  • Unity MCP packages are community-maintained and vary a lot in maturity.
  • Licensing and pricing history makes some developers cautious. Check current terms.
Verdict: a safe, well-trodden path. It is best if you already know Unity.

Blender → Godot Blender MCP + Godot MCP · GDScript

Pros

  • .tscn, .tres and .gd are plain text, so AI can read and edit scenes directly, which cuts reliance on screenshots and tokens.
  • Fastest iteration loop: seconds, with a tiny editor and instant script reload.
  • Native glTF import with extras exposed to post-import scripts, and Blender's glTF exporter fits it well.
  • Forward+ renderer has volumetric fog, glow, SSR and SDFGI, which is enough for blue-grey storm mood.
  • Free, MIT, no royalties, and a small export footprint for Steam.
  • You can keep tweaking it after week 4 without license concerns.

Cons

  • No built-in ocean or buoyancy. You write or adapt a wave shader and fake the boat's float.
  • Smaller asset ecosystem and fewer ready-made weather systems.
  • GDScript has less training data than C#, so expect more hallucinated APIs. Pin to the Godot 4.x docs in your prompt.
  • Godot MCP servers are young and fast-moving, and you may end up patching one.
  • Top-end lighting is below Unreal and HDRP, and you cannot brute-force realism.
Verdict: the best fit for a solo, token-limited, atmosphere-first prototype.

Blender → Unreal Blender MCP + Unreal MCP · Blueprints / C++ / Python

Pros

  • Best out-of-the-box atmosphere: Lumen, volumetric fog and clouds, Niagara rain, sky and lightning.
  • Water plugin and Chaos buoyancy cover the boat and sea.
  • Lumen and Nanite save hand-tuned lighting and LODs, which suits a small, moody scene.
  • Editor Python scripting exposes a lot of automation to an MCP.

Cons

  • Blueprints are binary graphs. AI cannot read or diff them well, so you fall back to C++ or Python, and your iteration cost rises.
  • C++ compile cycles, shader compiles and cooking make every loop slow.
  • Heavy install and RAM, and a lot of configuration surface for one person.
  • A 4-week prototype is likely to be spent fighting the tooling rather than polishing mood.
  • Unreal MCP tooling is the least mature of the three, so expect gaps.
  • 5% royalty above the revenue threshold. Check current terms.
Verdict: the best-looking ceiling and the worst fit for a solo 4-week sprint. A reasonable later port target.

Proposal: Script-first, manifest-driven Blender headless + MCP for look-dev + thin engine importer

Pros

  • Reproducible. Claude writes bpy scripts into your repo, and re-running one is free. A live MCP session pays tokens every time.
  • Engine-agnostic. The manifest is the contract. Switching engines after the week 1 spike costs one importer, not a rebuild.
  • Gameplay data lives in Blender. Empties named HAZ_rock_03, ANCHOR_lamp, SPAWN_boat or SIGHT_ship carry hazard placement, boat spawn and the lamp-room sightline into the engine.
  • Fits the pillars. Hazard density and sightlines are authored data you can retune, which supports "dread you can read".
  • Cheap to continue after week 4. New modules re-run the same scripts.

Cons

  • Up-front cost: the manifest schema and importer take about a day or two in week 1.
  • Less "magic". You will not watch the model being sculpted live, so look-dev still needs MCP sessions.
  • Procedural bpy modelling gives modular and brutalist forms well. Organic rocks and cliffs need noise and displacement tricks, or scanned assets.
  • You maintain the scripts, and the discipline of keeping them tidy is yours.
Verdict: recommended. It works with any of the three engines.

The proposal in practice

Built around your constraints, with atmosphere work protected from being squeezed out.

The manifest contract

{
  "asset": "lighthouse_lamp_room",
  "file": "lighthouse_lamp_room.glb",
  "anchors": [
    {"name": "ANCHOR_lamp",  "type": "burner_socket", "pos": [0, 1.2, 0]},
    {"name": "SIGHT_ship",   "type": "sightline",     "target": "ship_route_end"},
    {"name": "HAZ_rock_03",  "type": "hazard",        "radius": 4.0, "phase": "return"}
  ],
  "collision": "auto_convex_proxy",
  "notes": "Windows must keep a clear line to the island rocks (fail-state contract)."
}

Four-week plan

1
Week 1 · Pipeline spike and steering. Run an hour-long MCP test per engine and pick one. Block out the lighthouse, boat and a rock field with greybox scripts. Build the manifest importer. Go/no-go: is steering fun and are hazards readable?
2
Week 2 · Crossings. Outbound and return routes, hazard density by phase, ship deadline hidden clock, Jeff's placeholder shouted directions, sea surface as atmosphere only (no wave physics).
3
Week 3 · Lighthouse and story beats. Two repairs, window sightline to the rowboat, gate, boarding, burner pickup, final repair, win and fail outcomes. Lock Ted's presence by the end of this week.
4
Week 4 · Atmosphere pass. Fog falloff, lightning, rain, ship lights approaching, buoy bells, foghorn, lamp beam. Placeholder audio replaced where cheap. Keep a buffer for bugs. Waves stay a stretch goal and are cut first.

Making a monthly token budget last

  • Write bpy and engine scripts once, commit them, and re-run them. Don't regenerate meshes through chat.
  • Use MCP for look-dev: lighting, fog and composition checks. Use scripts for bulk work.
  • Take screenshots at low resolution and only after meaningful changes. Prefer text queries ("list objects", "dump scene tree") over images.
  • Keep a CLAUDE.md with engine version, naming conventions, the manifest schema and the pillars so each session starts with context rather than re-explaining.
  • Use a cheaper model for boilerplate and a stronger one for steering feel, state machines and debugging.
  • If the budget runs short late in the month, queue pure-Blender work for headless scripts and save the engine-MCP sessions for the atmosphere pass.

Atmosphere is mostly engine-side

The mood comes from fog density, light colour, lightning flashes, rain, sound design and the beam, not from mesh detail. Don't spend Blender tokens on fine geometry. Keep the Blender output modular and low-poly with good silhouettes, and put your effort into lighting and audio.
